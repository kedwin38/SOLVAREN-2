## 1. Platform Fundamentals (applies to all APIs)

### 1.1 Authentication (OAuth)
- Generate an access token **before** any API call via the Authorization API (the only **GET** endpoint on Daraja).
  - Sandbox: `https://sandbox.safaricom.co.ke/oauth/v1/generate?grant_type=client_credentials`
  - Production: `https://api.safaricom.co.ke/oauth/v1/generate?grant_type=client_credentials`
- Credentials = app **Consumer Key** (username) + **Consumer Secret** (password), Basic auth.
- **Token expires after 1 hour** — regenerate before expiry.
- All M-PESA APIs on Daraja are **POST** except the Authorization API (**GET**).

### 1.2 Environments
| Environment | Base URL |
|---|---|
| Sandbox (testing) | `https://sandbox.safaricom.co.ke` |
| Production (live) | `https://api.safaricom.co.ke` |

### 1.3 Asynchronous pattern (most APIs)
1. Org sends request → Daraja validates/authenticates/authorizes → forwards to M-PESA.
2. Daraja returns a **synchronous acknowledgement** (`ResponseCode: "0"` = accepted).
3. M-PESA processes, then delivers the actual result to your **ResultURL** (callback).
4. If the callback cannot be delivered (network), **there are NO automatic retries** — manually check the M-PESA portal or use Transaction Status API.
5. **QueueTimeOutURL** receives notification if the request times out awaiting processing.

Key sync/async split:
- **Asynchronous:** B2C, B2C Account Top Up, Transaction Status, Account Balance, Reversals, Pull Transactions
- **Synchronous:** B2C Hakikisha, Authorization (token)

Consume via internet, VPN, or Multiprotocol Switch.

### 1.4 Prerequisites (all APIs)
1. Daraja account on the Safaricom Developer Portal.
2. Create a sandbox app → get Consumer Key & Consumer Secret (My Apps).
3. Test data available in the simulator section (login required).
4. For production: live paybill/till/B2C shortcode with Business Admin/Manager operators created.

### 1.5 Common ID conventions
| ID | Meaning |
|---|---|
| `OriginatorConversationID` | Unique ID generated by **merchant system** per request (prevents double disbursement; used to query status). Must be unique — duplicates rejected (`500.002.1001`). |
| `ConversationID` | Unique ID returned by **M-PESA** per request (e.g. `AG_20240706_20106e9209f64bebd05b`). |
| `TransactionID` | M-PESA receipt number (e.g. `SG632NMUAB`) — also SMS'd to customer. Used for status queries and reversals. |
| `ResponseCode` / `ResultCode` | `0` = success/accepted; anything else = error/failure. |

### 1.6 Security Credential generation
M-PESA Core authenticates by decrypting the security credential:
1. Write the unencrypted (base64-encoded) initiator password into a byte array.
2. Encrypt with M-PESA's **public key (X509 certificate)** using **RSA with PKCS #1.5 padding (NOT OAEP)**.
3. Base64-encode the resulting byte array → that string is the `SecurityCredential`.
- Can be **reused** across multiple requests (no need to regenerate per call).
- Portal password rules: restrict special chars to `#`, `&`, `%`, `$`. **Avoid `@` and `.`** (e.g. `(`, `)` rejected; `@` treated as a normal char). Password valid for **90 days**.

## 2. Generic Error Response Codes (platform-wide)

Error body shape:
```json
{ "requestId": "...", "errorCode": "500.002.1001", "errorMessage": "Duplicate OriginatorConversationID." }
```
- `requestId` — unique ID assigned by API gateway
- `errorCode` — unique error code
- `errorMessage` — human-readable failure description

| Error | Possible Cause | Mitigation |
|---|---|---|
| `500.003.1001` Internal Server Error | Server failure | Verify your setup, correct endpoints, server running as expected |
| `400.003.01` Invalid Access Token | Wrong/expired access token | Regenerate token, use before expiry; check copy-paste accuracy |
| `400.003.02` Bad Request | Something missing in request | Follow API documentation exactly |
| `500.003.03` Quota Violation | Requests violate M-PESA TPS speed | For testing, send one request at a time |
| `500.003.02` Spike Arrest Violation | Your endpoints generate errors causing performance spikes | Ensure your endpoints/server are running, responding, and internet-accessible |
| `404.003.01` Resource not found | Wrong endpoint | Call the correct M-PESA API endpoint |
| `404.001.04` Invalid Authentication Header | Misplaced headers / wrong HTTP method | All Daraja M-PESA calls are POST except Authorization (GET) |
| `400.002.05` Invalid Request Payload | Malformed request body | Match the sample request payload exactly; avoid typos |
| `404.001.03` Invalid Access Token | Token invalid | Regenerate and use before expiry (HTTP 404) |
| `400.002.02` Bad Request – Invalid XXXX | Payload field invalid | Set payload per documentation (HTTP 400) |
| `404.001.01` Resource not found | Wrong endpoint | Correct API endpoint (HTTP 404) |
| `500.001.1001` Internal Server Error | Payload/setup issue | Ensure payload matches docs (HTTP 500) |
| `401.002.01` Invalid Access Token – XXX | Expired/incorrect token | Regenerate within 1h; correct credentials (HTTP 401) |
| `405.001` Method Not Allowed | Wrong HTTP verb | Use POST (HTTP 405) |
| `500.002.1001` Duplicate OriginatorConversationID | Reused originator ID | Unique OriginatorConversationID per request (HTTP 500) |
| `401.001` Invalid Access Token (Pull API) | Wrong consumer key/secret combo | Correct key+secret; regenerate hourly |

## 3. M-PESA Organization Shortcode Account Types

| B2C Accounts | Paybill Accounts | Buy Goods Accounts | Description |
|---|---|---|---|
| Utility | Utility | **Merchant** | Receives payments (paybill/buy goods). In B2C it is the **disbursement** account — B2C transactions debit the **Utility account**. |
| Working (MMF) | Working | Working | Transition account holding money awaiting settlement to bank / personal M-PESA. |
| Charges paid | Charges paid | Charges paid | Deducts charges per business tariff; always accrues a **negative** balance that must be settled before withdrawal. |
| Organization Settlement | — | (after charges) | Settles charges paid, then auto-moves Utility balance to Working ("Move funds Utility→MMF" is obsolete). |

**Fund flow tip:** If B2C reports insufficient balance despite funds, money is in MMF/Working but B2C debits Utility. Move funds via portal (My Functions → Initiate Transaction → Business Services – Move Funds from MMF to Utility → requires second operator approval under My Tasks → Group Task) or automate via B2B API with `CommandID: BusinessTransferFromMMFToUtility` (whitelisting required — apisupport@safaricom.co.ke).

## 4. M-PESA Organization Portal (org.ke.m-pesa.com)

### 4.1 Access
- URL: `https://org.ke.m-pesa.com/orglogin.action`
- Requires **Business Administrator** role under your shortcode; created by Safaricom.
- Pre-step: settlement option on the shortcode must be **Bank**, applied for via a **Head Office** application → email **M-PESABusiness@Safaricom.co.ke** for forms; they also guide Business Administrator creation.
- Dormant Business Administrator → email M-PESABusiness@Safaricom.co.ke to activate.

### 4.2 First-time login
1. Browse to https://org.ke.m-pesa.com
2. Enter shortcode (bulk payment number) + Business Administrator username + first-time password (case-sensitive; the full stop in the email is NOT part of the password).
3. Enter displayed verification code → login.
4. Enter OTP → change-password page → enter first-time password → set new password.
5. Confirm password + security question + two mandatory security answers.
6. Submit → account activated. Subsequent logins: username, shortcode, password, verification code + SMS OTP.

### 4.3 Portal roles
- **Business Administrator** — creates system users and assigns roles; cannot view transactions; created by Safaricom. Can create: Business Web Operator (initiate txns, statements, balance), Business Manager, Business Auditor (view-only). Also unlocks locked API user passwords.
- **Business Manager** — views statements, initiates transactions, approves/rejects transactions, withdraws funds; holds "Set Restricted ORG API PASSWORD" role used to set API user passwords.
- **Business Web Operator** — initiate transactions, statements, balance.
- **Business Auditor** — read-only.

### 4.4 Creating a Business Manager
1. Login as Business Administrator → Operators → Add.
2. Enter username, Access Channel = **Web**, Web Profile = default rule profile.
3. Assign roles: **Business Manager** + **Set Restricted ORG API PASSWORD**.
4. Enter KYC info → submit.

### 4.5 Creating an API user (initiator)
1. Login as Business Administrator → Operators → Add.
2. Enter API initiator username, Access Channel = **API**, default rule profile.
3. Assign relevant API roles (see table below).
4. Enter KYC info → submit.
5. **Set the password**: login as a user with Set Restrict Password role (Business Manager) → My Functions → Operator Management → search API username → Operations/Details → Set Password (avoid `@` and `.`). Until set, the API user stays "pending active".

### 4.6 API role assignments
| API | Portal Role |
|---|---|
| B2C | ORG B2C API Initiator |
| Business Pay Bill | Business Paybill Org API initiator |
| Business Buy Goods | Business Buy Goods Org API initiator |
| Transaction Status | Transaction Status query ORG API |
| Account Balance | Balance Query ORG API |
| Reversals | Org Reversals Initiator |
| Tax Remittance | Tax Remittance to KRA API |
| B2C Account Top Up | Org Business Pay to Bulk API initiator |
| Set Password role | Set Restricted ORG API PASSWORD |

## 5. API Reference

### 5.1 B2C (Business to Customer / Bulk Disbursements)

**Purpose:** Pay customers from a business shortcode. Use cases: salaries, cashback, promotional payouts, winnings, financial-institution withdrawals, loan disbursements.

**Go-live requirement:** Bulk Disbursement Account (or convert paybill/till to "one account" that can receive + disburse) — apply at https://www.safaricom.co.ke/business/sme/m-pesa-payment-solutions or https://m-pesaforbusiness.co.ke/.

| Env | URL |
|---|---|
| Sandbox | `https://sandbox.safaricom.co.ke/mpesa/b2c/v3/paymentrequest` |
| Production | `https://api.safaricom.co.ke/mpesa/b2c/v3/paymentrequest` |

**Request body:**
```json
{
  "OriginatorConversationID": "600997_Test_32et3241ed8yu",
  "InitiatorName": "testapi",
  "SecurityCredential": "RC6E9WDxXR4b9X2c6z3gp0oC5Th==",
  "CommandID": "BusinessPayment",
  "Amount": "10",
  "PartyA": "600992",
  "PartyB": "254705912645",
  "Remarks": "remarked",
  "QueueTimeOutURL": "https://mydomain.com/path",
  "ResultURL": "https://mydomain.com/path",
  "Occassion": "ChristmasPay"
}
```

**Request parameters:**
| Name | Description | Type | Optional |
|---|---|---|---|
| OriginatorConversationID | Unique merchant-generated ID per request (double-disbursement guard; used for status queries) | String | No |
| InitiatorName | API operator username on M-PESA portal | String | No |
| SecurityCredential | Encrypted API-user password | String | No |
| CommandID | `SalaryPayment` (registered customers only now), `BusinessPayment` (registered customers), `PromotionPayment` (registered; congratulatory SMS) | String | No |
| Amount | Transaction amount | Numeric | No |
| PartyA | B2C org shortcode sending money | Numeric | No |
| PartyB | Customer MSISDN, 12-digit, no `+` (e.g. 254705912645) | Numeric | No |
| Remarks | 2–100 chars | String | No |
| QueueTimeOutURL | Timeout notification URL | URL | No |
| ResultURL | Result callback URL | URL | No |
| Occassion | 1–100 chars (note the spelling "Occassion" in the API) | String | Yes |

**Sync response:**
```json
{
  "ConversationID": "AG_20240706_20106e9209f64bebd05b",
  "OriginatorConversationID": "600997_Test_32et3241ed8yu",
  "ResponseCode": "0",
  "ResponseDescription": "Accept the service request successfully."
}
```

**Success callback (ResultURL) keys:** `TransactionAmount`, `TransactionReceipt`, `ReceiverPartyPublicName`, `TransactionCompletedDateTime` (dd.MM.yyyy HH:mm:ss), `B2CUtilityAccountAvailableFunds`, `B2CWorkingAccountAvailableFunds`, `B2CRecipientIsRegisteredCustomer` (Y/N), `B2CChargesPaidAccountAvailableFunds`, plus `ReferenceData.ReferenceItem.QueueTimeoutURL`.

**Result codes:**
| ResultCode | ResultDesc | Explanation |
|---|---|---|
| 0 | Processed successfully | Success |
| 1 | Balance insufficient | Not enough in **Utility** account |
| 2 | Limit rule (below minimum) | Amount below allowed minimum |
| 3 | Limit rule (above maximum) | Amount above allowed max |
| 4 | Would exceed daily transfer limit | Customer daily limit Ksh 500,000 |
| 8 | Would exceed maximum balance | Customer max account balance Ksh 500,000 |
| 11 | DebitParty invalid state | B2C account not active |
| 21 | Initiator not allowed | Missing ORG B2C API initiator role |
| 2001 | Initiator information invalid | Wrong username/password/encryption/cert |
| 2006 | Account rule decline | B2C account not active |
| 2028 | Not permitted per product assignment | PartyA lacks B2C permission |
| 2040 | Credit party type unsupported | Customer not registered |
| 8006 | Security credential locked | Password locked; Business Admin unlocks |
| SFC_IC0003 | Operator does not exist | Invalid/nonexistent phone number |

**Limits:** min Ksh 10; max per transaction Ksh 250,000; customer max balance Ksh 500,000; max daily value Ksh 500,000.

**B2C FAQs distilled:**
- Async: acknowledgement is immediate; success = callback `ResultCode 0`.
- No passkey needed (passkey is only for STK Push/Express).
- No manual approval needed for API-initiated B2C.
- Status can be checked via Transaction Status API (OriginatorConversationID or receipt number).
- B2C reversals **not** supported via API — manual on M2 portal.
- Paybill → B2C funding: use **B2C Account Top Up API** (paybill Working → B2C Utility).
- Simulator only works with sandbox test shortcodes, not live ones.
- Duplicate OriginatorConversationID → `500.002.1001`.

### 5.2 B2C Account Top Up (B2B endpoint)

**Purpose:** Load funds into a B2C shortcode's Utility account for disbursement. Moves money from your MMF/Working account to the recipient's Utility account. (Also referenced for paybill→B2C funding.)

| Env | URL |
|---|---|
| Sandbox | `https://sandbox.safaricom.co.ke/mpesa/b2b/v1/paymentrequest` |
| Production | `https://api.safaricom.co.ke/mpesa/b2b/v1/paymentrequest` |

**Request body:**
```json
{
  "Initiator": "testapi",
  "SecurityCredential": "<encrypted password>",
  "CommandID": "BusinessPayToBulk",
  "SenderIdentifierType": "4",
  "RecieverIdentifierType": "4",
  "Amount": "239",
  "PartyA": "600979",
  "PartyB": "600000",
  "AccountReference": "353353",
  "Requester": "254708374149",
  "Remarks": "OK",
  "QueueTimeOutURL": "https://mydomain/path/timeout",
  "ResultURL": "https://mydomain/path/result"
}
```

**Parameters:** `CommandID` must be `BusinessPayToBulk` only. Initiator needs **Org Business Pay to Bulk API initiator** role. `PartyA` = your shortcode (debit), `PartyB` = receiving B2C shortcode. Both identifier types must be `"4"`. `Requester` optional MSISDN. Response is standard ack (`OriginatorConversationID`, `ConversationID`, `ResponseCode 0`).

**Success callback keys:** `DebitAccountBalance` (`{Amount={CurrencyCode=KES, MinimumAmount=..., BasicAmount=...}}`), `Amount`, `DebitPartyAffectedAccountBalance` (`Working Account|KES|...`), `TransCompletedTime` (14-digit `yyyyMMddHHmmss`), `DebitPartyCharges` (empty if none), `ReceiverPartyPublicName`, `Currency`, `InitiatorAccountCurrentBalance`, `ReferenceItem` (`BillReferenceNumber`, `QueueTimeoutURL`). Failure sample: `ResultCode 2001` "The initiator information is invalid", generic `TransactionID: OAK0000000`.

**Note:** B2B API also used with `CommandID: BusinessTransferFromMMFToUtility` to automate MMF→Utility movement (whitelisting required).

### 5.3 Transaction Status

**Purpose:** Secondary reconciliation when callbacks are missed. Requires an **M-PESA Receipt number (TransactionID)** or **OriginatorConversationID** of the transaction. Works for C2B, B2B, B2C, Reversal, and IMT transactions.

| Env | URL |
|---|---|
| Sandbox | `https://sandbox.safaricom.co.ke/mpesa/transactionstatus/v1/query` |
| Production | `https://api.safaricom.co.ke/mpesa/transactionstatus/v1/query` |

**Request body:**
```json
{
  "Initiator": "testapiuser",
  "SecurityCredential": "<encrypted>",
  "CommandID": "TransactionStatusQuery",
  "TransactionID": "NEF61H8J60",
  "OriginalConversationID": "7071-4170-a0e5-8345632bad442144258",
  "PartyA": "600782",
  "IdentifierType": "4",
  "ResultURL": "http://myservice:8080/transactionstatus/result",
  "QueueTimeOutURL": "http://myservice:8080/timeout",
  "Remarks": "OK",
  "Occasion": "OK"
}
```

**Key params:** `CommandID` only `TransactionStatusQuery`; `PartyA` = org shortcode (6–9 digits) or MSISDN (12 digits); `IdentifierType` `4` = org shortcode; `Occasion` optional (≤100 chars); `OriginalConversationID` = originator conversation ID of the transaction being checked.

**Callback keys:** `DebitPartyName` (twice — org then customer), `OriginatorConversationID`, `InitiatedTime`, `DebitAccountType` (e.g. "Utility Account"), `DebitPartyCharges` (`Fee For B2C Payment|KES|22.40`), `TransactionReason`, `ReasonType` (e.g. "Business Payment to Customer via API"), **`TransactionStatus`** (`Completed` etc.), `FinalisedTime`, `Amount`, `ConversationID`, `ReceiptNo`.

**Transaction lifecycle statuses:** `Initiated` (pending revalidation) → `Authorized`/`Pending Authorized` (awaiting credit-party validation) → Final: `Cancelled` / `Declined` / `Completed` / `Expired`.

**Result codes:** `0` success; `SFC_IC0003` operator does not exist. (Plus the generic error table in §2.)

### 5.4 Account Balance

**Purpose:** Programmatically check org M-PESA balances. Use cases: reconciliation, pre-payment fund checks, fraud monitoring, multi-branch cash-flow, payroll pre-checks, bill-payment tracking.

| Env | URL |
|---|---|
| Sandbox | `https://sandbox.safaricom.co.ke/mpesa/accountbalance/v1/query` |
| Production | `https://api.safaricom.co.ke/mpesa/accountbalance/v1/query` |

**Request body:**
```json
{
  "Initiator": "testapiuser",
  "SecurityCredential": "<encrypted>",
  "CommandID": "AccountBalance",
  "PartyA": "600000",
  "IdentifierType": "4",
  "Remarks": "ok",
  "QueueTimeOutURL": "http://myservice:8080/queuetimeouturl",
  "ResultURL": "http://myservice:8080/result"
}
```

**Params:** `CommandID` = `AccountBalance` (max 64); `PartyA` = org shortcode querying; `IdentifierType` = `4`; standard Initiator/SecurityCredential/Remarks/URLs. Initiator needs **Balance Query ORG API** role.

**Callback:** `ResultParameter` array contains `AccountBalance` (all accounts, `&`-separated, pipe-delimited fields) and `BOCompletedTime` (14-digit).

`Working Account|KES|700000.00|700000.00|0.00|0.00&Float Account|KES|0.00|0.00|0.00|0.00&Utility Account|KES|228037.00|228037.00|0.00|0.00&Charges Paid Account|KES|-1540.00|-1540.00|0.00|0.00&Organization Settlement Account|KES|0.00|0.00|0.00|0.00`

**Notes:** Real-time balance; can only query **your own** shortcode (or merchant stores within your hierarchy); no auto-retry on failed callbacks (use Transaction Status); scheduling/automation allowed.

### 5.6 Pull Transactions (C2B reconciliation)

**Purpose:** Reconciliation tool — query **all C2B transactions** under your paybill/till for the **last 48 hours**; recovers transactions whose callbacks were missed. C2B only (no B2C/B2B).

| Env | Register (POST) | Query (GET†) |
|---|---|---|
| Sandbox | `https://sandbox.safaricom.co.ke/pulltransactions/v1/register` | `https://sandbox.safaricom.co.ke/pulltransactions/v1/query` |
| Production | `https://api.safaricom.co.ke/pulltransactions/v1/register` | `https://api.safaricom.co.ke/pulltransactions/v1/query` |

† Docs state POST for Register, GET for Query (query carries a JSON body per samples).

**Register Pull (one-time):**
```json
{
  "ShortCode": "600000",
  "RequestType": "Pull",
  "NominatedNumber": "0722000000",
  "CallBackURL": "https://domain/path"
}
```
- `NominatedNumber` = Safaricom MSISDN associated with the org account (found on M-PESA portal under shortcode KYC details).
- Response: `ResponseRefID`, `ResponseStatus`/`ResponseCode`, `ShortCode`, `ResponseDescription`.
- Codes: `1000` registered successfully; `1001` already registered.

**Query Pull:**
```json
{
  "ShortCode": "600000",
  "StartDate": "2020-08-04 8:36:00",
  "EndDate": "2020-08-16 10:10:00",
  "OffSetValue": "0"
}
```
- `OffSetValue` = pagination offset (starts 0; e.g. 100 to fetch rows 101–200).
- Response rows: `transactionId`, `trxDate` (ISO `2020-08-05T10:13:00Z`), `msisdn`, `sender`, `transactiontype` (e.g. `c2b-pay-bill-debit`), `billreference`, `amount`, `organizationname`.
- Codes: `1000` success; `1001` null / no transactions in range (body `"Transaction": "[[]]"`). Errors: `400.001` invalid shortcode; `401.001` invalid token; `500` no available transactions.

**Headers:** `Content-Type: application/json`, `Authorization: Bearer access_token` (+ `Accept-Encoding` on register).

### 5.7 B2C Hakikisha (identity validation)

**Purpose:** Validate customer identity by phone number **before** a B2C payout; returns masked names. Use cases: disbursement safety (customer sees recipient name), fraud prevention (mistyped numbers / account-swap), reversal reduction. **Synchronous.** Offered reciprocally with the C2B Hakikisha API under contract.

**Onboarding:** Not self-serve — write to apisupport@safaricom.co.ke or your account manager; contractual agreements required; production access after approval.

| Env | URL |
|---|---|
| Sandbox | `https://sandbox.safaricom.co.ke/mpesa/b2c/hakikisha/v1/hakikisha` |
| Production | Via onboarding (not listed) |

**Request:**
```json
{
  "header": {
    "requestID": "8aeefeea-8713-4a4d-b1b4-7b8c143b7ec1",
    "timestamp": "1748933384"
  },
  "body": { "msisdn": "254722000000", "shortcode": "123456" }
}
```

**Response:**
```json
{
  "header": { "requestID": "...", "timestamp": "...", "status": "200", "message": "Success" },
  "body": { "firstName": "john", "middleName": "M******", "lastName": "M******" }
}
```
- Middle/last names masked. Errors: `400` bad request / invalid phone ("The customer does not exist."), `401.001` invalid access token.
- **Safaricom (Kenyan) MSISDNs only** — no international numbers. Free API but requires approval.

## 6. Go Live (all APIs)

1. Finish development/testing in sandbox.
2. Navigate to the **GO LIVE** tab on Daraja; provide:
   - Live shortcode (paybill/till/B2C as applicable),
   - Organization name (shortened, no symbols/special chars),
   - M-PESA username of operator with **Business Administrator or Business Manager** role (case-sensitive).
3. OTP for Go Live is sent to the Safaricom number on that user's M-PESA portal profile.
4. On success: production endpoints emailed to developer; sandbox app moves to production with production consumer key/secret (Dashboard → My Apps → Production Apps).
5. For B2C specifically: needs a Bulk Disbursement Account / one-account shortcode.
6. "Invalid API call as no apiproduct match found" in production → ensure the relevant product is enabled on your Daraja app + correct endpoint.
7. Apply for live paybill/till/B2C: **M-PESABusiness@Safaricom.co.ke** or https://m-pesaforbusiness.co.ke/.

## 7. Testing

- **Option 1 — Daraja Simulator** (login required): create test app, select the API product, simulator auto-picks app credentials + predefined test data (incl. sandbox `InitiatorName` / `InitiatorPassword` and password-encryption tool under Test Credentials).
- **Option 2 — Postman**: generate token from oauth endpoint, then call API with your credentials. "Use API" button (logged in) gives a pre-built collection.
- C2B simulation: register URLs first; `CustomerPayBillOnline` for paybill, `CustomerBuyGoodsOnline` for till.
